Agenda 01 • Konteks Sistem

1. Profil & Konteks Bisnis Database Fajar Cell

Memahami karakteristik operasional toko retail ponsel dan implikasinya terhadap arsitektur basis data.

📱 Serial Item Tracking (IMEI) Unik per Unit
Berbeda dengan retail biasa, produk smartphone adalah barang serial bernilai tinggi. Setiap unit memiliki Nomor IMEI unik, kondisi fisik (Baru/Second), Battery Health, harga modal kulakan yang fluktuatif, serta garansi resmi/toko.
🔄 Transaksi Tukar Tambah (Trade-In) Dual Alur
Alur bisnis di mana pembeli menukarkan HP lama miliknya untuk memotong harga HP baru. Transaksi ini secara simultan bertindak sebagai Penjualan Unit Baru sekaligus Pembelian Unit Bekas dalam 1 nomor nota transaksi.
💳 Penjualan Kredit & Komisi Sales Finansial
Mendukung skema termin bayar (Cash, Transfer, DP, cicilan bertempo dengan bunga) yang melahirkan Piutang Pelanggan, serta pembagian insentif komisi sales per unit transaksi yang harus diaudit ketat.
Spesifikasi Lingkungan Teknis: Database: fajar_cell | Engine: InnoDB | Lokasi: Fajar Cell Tuban (Jl. Pemuda No. 75) | Volume: 135 Nota • 71 Unit HP
Sistem Berjalan Aktif

3. Evaluasi Aturan Referensial (Delete/Update Rules)

Audit terhadap aksi Foreign Key Constraint: Mengapa pilihan `SET NULL` dan `CASCADE` menjadi bumerang bagi Fajar Cell.

Foreign Key Relationship Tabel Anak $\rightarrow$ Induk ON DELETE ON UPDATE Evaluasi Risiko DBA
detail_transaksi.id_unit_hp detail $\rightarrow$ unit_hp SET NULL NO ACTION FATAL: Jika unit HP terhapus dari gudang, histori nota kehilangan identitas barang terjual.
detail_transaksi.id_transaksi detail $\rightarrow$ transaksi CASCADE NO ACTION Nota dihapus langsung menghapus seluruh item transaksi tanpa riwayat log backup.
piutang.id_transaksi piutang $\rightarrow$ transaksi CASCADE NO ACTION KRITIS: Menghapus transaksi otomatis menghapus catatan sisa tagihan hutang pelanggan!
unit_hp.id_katalog unit_hp $\rightarrow$ katalog_produk RESTRICT NO ACTION AMAN: Mencegah penghapusan master katalog selama masih ada unit fisik tersisa.
transaksi.id_contact transaksi $\rightarrow$ contacts RESTRICT NO ACTION AMAN: Pelanggan/Supplier yang memiliki jejak nota tidak dapat dihapus sembarangan.
Bahaya #1: The Disappearing Items (SET NULL)
Di database akuntansi, data masa lalu tidak boleh diputus referensinya. Dengan SET NULL, laporan penjualan masa lalu bisa bernilai Rp 15 Juta tetapi field barangnya berubah menjadi kosong.
Bahaya #2: Accidental Debt Wipeout (CASCADE)
Jika kasir membatalkan nota transaksi kredit lama yang keliru, aturan CASCADE di tabel piutang akan langsung menghapus seluruh rekam jejak cicilan pembayaran yang sudah disetor debitur.
Presenter Script (Slide 7):
"Setelah melihat ERD-nya, mari kita evaluasi aturan referensialnya. Di sini kita menemukan dua anti-pattern besar. Pertama: relasi unit HP ke detail transaksi disetel ON DELETE SET NULL. Jika unit HP dihapus dari database gudang, riwayat penjualan masa lalu kehilangan jejak barang fisiknya! Kedua: piutang disetel CASCADE ke transaksi. Jika transaksi dihapus, seluruh tagihan hutang pelanggan ikut terhapus otomatis tanpa jejak."

4. Identifikasi Risiko Data (Temuan Nyata Audit)

Bukti hasil eksekusi query audit pada database localhost membuktikan kegagalan integritas data secara riil.

1. Inkonsistensi Data P1 Critical
• 10 Record Orphan Detail: id_unit_hp dan id_stok_aksesoris keduanya bernilai NULL.

• Disparitas Nilai Header vs Detail:
- Transaksi #24: Total Nota Rp 1,2 Jt vs Detail Rp 12 Jt (Selisih 10,8 Jt)
- Transaksi #30: Total Nota Rp 99 vs Detail Rp 9,85 Jt!
2. Redundansi & Anomali P1 Critical
• 11 Record Harga Satuan Negatif: Kasir memasukkan unit trade-in dengan harga minus hingga -Rp 13.700.000 karena tidak ada skema tukar tambah resmi.

• Komisi Sales Redundan di 3 Tempat: Tercatat di transaksi, detail_transaksi, dan transaksi_sales tanpa sinkronisasi otomatis.
3. Kehilangan & Keamanan P2 High
• Kehilangan Data Historis: Tidak ada fitur Soft Delete; penghapusan bersifat fisik (*hard delete*).

• Ketiadaan Jejak Audit Kasir: Tabel transaksi tidak memiliki kolom created_by.

• Plaintext Credentials: API Key pihak ketiga tersimpan polos di tabel settings.
Dampak Bisnis Nyata: Laporan laba-rugi toko, perhitungan komisi karyawan, dan stok gudang saat ini berada dalam kondisi bias dan tidak dapat diaudit secara akuntansi formal.

Agenda 04 • Prioritas & Mitigasi DBA

4. Prioritas Perlindungan & Langkah Mitigasi DBA

Matriks perlindungan sistem informasi dan script SQL DDL langsung untuk mengamankan engine database.

Prioritas 1 (P1 • CRITICAL): Integritas Finansial
• Pasang CHECK Constraint untuk menolak harga minus dan kuantitas 0.
• Pasang aturan XOR Item: baris detail wajib memilih HP atau Aksesoris, tidak boleh kosong keduanya.
• Ubah foreign key menjadi RESTRICT.
-- DDL Script Mitigasi Integritas Fajar Cell ALTER TABLE detail_transaksi ADD CONSTRAINT chk_harga_positif CHECK (harga_satuan >= 0), ADD CONSTRAINT chk_qty_positif CHECK (jumlah_qty > 0), ADD CONSTRAINT chk_item_terisi CHECK ( (id_unit_hp IS NOT NULL AND id_stok_aksesoris IS NULL) OR (id_unit_hp IS NULL AND id_stok_aksesoris IS NOT NULL) );
Prioritas 2 (P2 • HIGH): Proteksi & Disaster Recovery
• Backup Terjadwal: Full backup harian terkompresi via mysqldump pukul 02:00 WIB.
• Point-in-Time Recovery (PITR): Mengaktifkan MySQL Binary Log (log_bin=ON) untuk menjamin RPO < 5 menit.
• Principle of Least Privilege: User aplikasi app_pos hanya diizinkan SELECT, INSERT, UPDATE (cabut hak DROP/ALTER).
• Transaksi ACID Terisolasi: Checkout kasir wajib dibungkus dalam blok atomik START TRANSACTION ... COMMIT.
Kesimpulan Strategis DBA:
Mitigasi ini mengalihkan beban validasi dari front-end aplikasi ke Database Engine MySQL, sehingga integritas data terjamin 100% konsisten.
Presenter Script (Slide 10):
"Langkah terakhir adalah mitigasi dan prioritas perlindungan. Prioritas 1 kami adalah memasang constraint langsung di level DDL: harga wajib positif, kuantitas positif, dan detail transaksi wajib XOR (hanya HP atau aksesoris). Prioritas 2 kami adalah disaster recovery: backup terjadwal, pengaktifan binary log untuk Point-in-Time Recovery, dan membatasi hak akses user aplikasi agar tidak bisa melakukan DROP atau ALTER."
